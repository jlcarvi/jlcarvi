# GitHub Profile README Specification

## Purpose

Define behavior for an honest, static GitHub profile `README.md` for recruiters, engineering leaders, architects, and clients evaluating a Senior Cloud Data Infrastructure Engineer / Platform Architect.

## Requirements

### Requirement: Professional English Positioning

The README MUST use English-only, neutral/professional language and MUST lead with Senior Cloud Data Infrastructure Engineer / Platform Architect. It MUST make architecture depth, hands-on AWS/IaC execution, distributed systems, 7+ years Industrial IoT, TucanBit consulting, and contact path visible without positioning the owner as pure IoT, pure DevOps, AI engineer, junior/mid-level, or academic-first.

#### Scenario: 15-second seniority and identity scan

- GIVEN the README is opened on GitHub desktop
- WHEN a visitor scans headings and top bullets for 10-15 seconds
- THEN they identify seniority, Cloud/Data Platform identity, architecture, hands-on implementation, AWS+IaC, distributed-systems depth, and Industrial IoT specialization
- AND no non-English profile content is present

#### Scenario: Mobile first-screen scan

- GIVEN the README is opened on a mobile viewport
- WHEN the reader scans the top section
- THEN key positioning remains readable without wide tables or image-only content

### Requirement: Verified Public Facts

The README MUST include only approved public facts: Fribourg, Switzerland; Spanish native, English fluent, French B1 conversational; AWS Certified Solutions Architect – Associate; preparing AWS Certified Solutions Architect – Professional; Joint Navigation Satellite Programme training starting September 2026; PhD in Distributed Systems and Wireless Sensor Networks at University of Bern; Faculty of Science prize for doctoral dissertation.

#### Scenario: Public facts review

- GIVEN a reviewer checks credentials, education, location, and languages
- WHEN they compare the README with the profile brief
- THEN all listed public facts match the brief and use one 7+ years experience source

### Requirement: Space/GNSS Transferability

The README MUST present Space/GNSS as an emerging specialization and SHOULD explain the bridge: distributed systems + telemetry/IoT + cloud data infrastructure + networking + signal processing + positioning/coordinate systems → GNSS/satellite data infrastructure.

#### Scenario: 30-second Space/GNSS credibility check

- GIVEN a visitor scans beyond the opening for 30 seconds
- WHEN they read the Space/GNSS positioning
- THEN they understand why the background transfers and that the specialization is emerging
- AND engineering evidence remains grounded in existing cloud, data, distributed systems, and IoT work

### Requirement: Honesty and Public/Private Boundaries

The README MUST NOT invent projects, metrics, outcomes, client names, certifications, or professional satellite/ground-segment experience. It MUST NOT expose Swiss Permit C or detailed geographic market targeting.

#### Scenario: No invented space experience

- GIVEN the README mentions Space, GNSS, satellite data, or ground-segment-oriented platforms
- WHEN a reviewer evaluates the claim
- THEN it is framed as training, interest, or transferable expertise, not professional space experience

#### Scenario: Public/private boundary

- GIVEN private brief details exist
- WHEN README content is reviewed
- THEN Swiss Permit C and detailed market targeting are absent

### Requirement: Dual-Mode Evidence Journey

The README MUST support 10-15 second scan mode and deeper evaluation through concise evidence-backed sections. It SHOULD keep the PhD supportive, not dominant, and MAY include growth-ready project placeholders only when they are clearly future or real-history based.

#### Scenario: Deep technical review

- GIVEN an architect or client reads the full README
- WHEN they inspect technical evidence
- THEN they find architecture, implementation, AWS/IaC, distributed/data-intensive systems, Industrial IoT, and credible project guidance without keyword stuffing

### Requirement: Restrained Static Visuals

The README MUST remain static Markdown with no dynamic generation, GitHub Actions, tokens, or scheduled updates. It MAY use restrained badges/cards only as decorative support.

#### Scenario: Badges fail gracefully

- GIVEN badges or stats cards fail to load
- WHEN the README is read as plain Markdown
- THEN role, skills, credentials, links, and project guidance remain understandable

### Requirement: Links, Structure, and Manual Verification

The README MUST include LinkedIn `https://www.linkedin.com/in/jlcarvi/` and profile-relevant links only. It MUST use consistent headings, concise sections, meaningful alt text, working links, and manually verifiable GitHub rendering.

#### Scenario: Links resolve

- GIVEN a reviewer opens the rendered README
- WHEN headings, images, badges, and links are inspected
- THEN the profile is scannable, accessible, relevant, and free of broken links
