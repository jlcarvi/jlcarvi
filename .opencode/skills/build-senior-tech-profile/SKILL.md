# Build Senior Technical Profile

## Purpose

Create or improve a professional GitHub profile for a senior engineer.

The profile must communicate one coherent professional identity rather than
a collection of technologies, qualifications, and interests.

The target impression is:

> Senior Cloud Data Infrastructure Engineer / Platform Architect who combines
> architecture depth with hands-on implementation, with strong distributed
> systems and Industrial IoT experience and a credible trajectory toward
> Space/GNSS infrastructure.

## Required context

Before making recommendations or editing the profile:

1. Read `references/profile-brief.md`.
2. Read `references/review-checklist.md`.
3. Inspect the existing `README.md`.
4. Inspect the repository structure when relevant.

Treat `references/profile-brief.md` as the source of truth for professional
claims.

Never invent experience, projects, technologies, employers, metrics,
certifications, responsibilities, or industry expertise.

If information needed for the profile is missing, identify it instead of
guessing.

## Core positioning

Preserve this hierarchy:

1. Senior Cloud / Data Platform Engineering
2. Architecture + hands-on implementation
3. Distributed systems
4. Industrial IoT as a strong domain specialization
5. AWS / Terraform / Terragrunt as implementation evidence
6. Space / GNSS as an emerging specialization built on existing strengths

Industrial IoT must be visible but must not restrict the person to the title
"IoT Engineer".

The PhD must reinforce technical depth but must not become the primary
professional identity.

Space/GNSS positioning must be credible and forward-looking. Never transform
training or adjacent expertise into professional space-industry experience.

## Profile story

Everything should reinforce this story:

> I design and build secure cloud platforms for distributed and IoT-driven
> data systems, combining architecture depth with hands-on AWS and
> Infrastructure-as-Code execution.

Internal north star:

> Architecture depth. Hands-on execution. Distributed and IoT data systems.

## Audience

Optimize primarily for:

- Engineering Managers
- Heads of Engineering
- Platform and Cloud Architects
- CTOs
- Technical recruiters

The profile should also be attractive to engineering organizations working
in:

- satellite technology
- GNSS
- ground-segment data infrastructure
- telemetry systems
- Industrial IoT
- data-intensive industrial platforms

## Space/GNSS bridge

When appropriate, make the transferability visible:

Distributed systems
+ telemetry / IoT
+ cloud data infrastructure
+ networking
+ signal processing
+ positioning / coordinate systems
→ GNSS / satellite data infrastructure

Do not claim existing professional ground-segment or satellite engineering
experience unless explicitly supported by the profile brief.

## Style

The profile should feel:

- senior
- technical
- concise
- architecture-oriented
- evidence-oriented
- internationally readable

Avoid:

- generic enthusiasm statements
- "Hi, I'm..."
- excessive emojis
- large collections of badges
- skill progress bars
- long technology inventories
- AI marketing language
- keyword stuffing
- unsupported superlatives

Prefer engineering capabilities and problems over technology lists.

## Workflow

### Stage 1 — Analyze

Do not edit immediately.

First:

1. Read the required context.
2. Analyze the current profile.
3. Identify its current professional story.
4. Identify conflicting or weak signals.
5. Identify missing evidence.
6. Propose an information hierarchy.

### Stage 2 — Plan

Propose a concise README structure.

For every proposed section explain:

- what hiring-manager question it answers;
- how it strengthens the main professional story;
- whether the claim is currently supported.

Wait for human approval before significant restructuring.

### Stage 3 — Implement

After approval:

1. Update `README.md`.
2. Keep the content concise.
3. Preserve factual accuracy.
4. Do not manufacture content to make the profile appear complete.
5. Leave future project evidence out until it actually exists.

### Stage 4 — Review

Review the result against `references/review-checklist.md`.

Specifically check:

- Is seniority obvious?
- Is Cloud/Data Platform Engineering the primary identity?
- Is architecture visible?
- Is hands-on implementation visible?
- Is Industrial IoT visible without becoming restrictive?
- Is the PhD supporting rather than dominating?
- Is the Space/GNSS trajectory credible?
- Are current training and skills represented accurately?
- Are there unsupported claims?
- Are there too many competing identities?

### Stage 5 — Human gate

Show the proposed changes or diff.

Do not push to GitHub.

Do not make final positioning decisions on behalf of the owner.

The human owns final approval.
